# M2 durable file versions — issue #16 — T3

## Intent / completion scope

Publish a verified migrated JSON version persistently and restore an exact original byte snapshot to another new file. Original input paths and existing destinations are never overwritten or deleted. This append-only version model avoids lost updates without pretending Node provides atomic compare-and-swap replacement of arbitrary live files. In-place editing, ACL/xattr replication, automatic snapshot deletion, remote/network filesystems, Windows and automatic repair guesses are non-goals. Node22+ Linux/macOS local filesystems only.

## Existing system and flow

Reuse schema-bound MigrationPlan v1 and dryRunMigration (#14). CLI parses explicit file targets. New snapshot reader captures bounded regular files with no-follow/nonblocking descriptors, strict UTF-8, stable pre/post identity and raw SHA256. A bounded private worker verifies schemas/source/target/rollback on captured JSON values. Only after verification does the main process create durable private transaction artifacts. The deterministic core/package root exports remain unchanged.

Flow: explicit stage inputs → snapshots/worker validation → new private transaction directory → immutable manifest published last → explicit apply → atomic hardlink publication to new destination → append-only applied marker → explicit restore → immutable restore intent → atomic original-byte publication to new destination → restored marker. Inspect is read-only. No CLI command overwrites a source, destination, snapshot or marker.

## Domain / invariant

A transaction binds a source byte revision, exact schemas and plan snapshots, a candidate revision, a user-selected migrated destination, and publication inode identities. A prepared transaction is a reviewable capability record, not a signature or external authorization. Snapshot confidentiality relies on local owner-only permissions. Output hashes identify content; retained private publication hardlinks preserve inode identity across interruption.

## Commands / requirements and acceptance

TX-1 `stage <old> <new> --document file --plan file --transaction NEW_DIR --output NEW_FILE`: verify captured inputs with existing 5s/128MiB worker limits; reject source/target/rollback failure before persistence. Capture originals byte-for-byte. Require trusted local owner/root path ancestry and owner-only transaction directory (0700); snapshots 0400, publication copies 0600. Complete source/schema/plan/candidate inputs remain ≤1MiB/depth64. Source JSON must be strict UTF-8, regular, final non-symlink. Reject changing identity/bytes during read. Source untouched. Return prepared summary with hashes/paths, never values.
TX-2 `apply --transaction DIR --document ORIGINAL --output MIGRATED`: require explicit canonical paths match manifest; revalidate immutable snapshot digests, version, shape, private ownership/permissions and worker proof. Before first publication, current source identity and raw bytes must match staged revision. Final target must not exist. Publication is same-filesystem link(existing publication payload, new target): atomic no-replace. Sync file/parent directories; then publish deterministic applied marker with no-replace. Never unlink source or output. Two transactions racing for one target: at most one wins; unrelated existing files, even identical bytes, are refused. Two identical applies of one transaction are idempotent by retained publication inode+hash.
TX-3 `restore --transaction DIR --document MIGRATED --output NEW_RESTORE`: require valid applied marker and unchanged applied inode/content, revalidate snapshots and schemas/rollback proof. Bind the first explicit restore destination through immutable restore-intent publication; competing different destinations conflict. Publish original exact bytes using a distinct retained publication payload inode, new-file no-replace. Confirm restored byte hash before deterministic restored marker. Original source and migrated file remain intact. Repeat same restore idempotently; changed outputs/conflicting destinations fail closed.
TX-4 `inspect-transaction --transaction DIR`: read-only phase report: prepared, apply-pending (owned output linked before marker), applied, restore-pending (intent/link before marker), restored, incomplete. Recovery is repeat apply/restore for matching pending state. An interrupted stage without final manifest is incomplete: retain it and stage afresh in a new directory. Missing/tampered artifacts, symlinks, wrong ownership/modes/hashes, unexpected marker content or externally changed outputs are errors; never auto-delete or take over a stale lock. Protocol is lock-free: immutable intent and no-replace artifacts give idempotence and avoid stale process locks.
TX-5 Version1 public transaction format has fixed artifact names: original.json, candidate.json, source-schema.json, target-schema.json, plan.json, apply.payload, restore.payload, manifest.json; applied.json, restore-intent.json, restored.json are optional append-only markers. No manifest-controlled arbitrary artifact paths. Marker creation uses fsynced exclusive temp files plus hardlink to final name (atomic no-replace), never overwrites. Leftover private temp files are harmless and not automatically purged. Only publication payloads are hardlinked to outputs, so mutable outputs cannot modify immutable snapshots.
TX-6 Failures after output publication remain recoverable using the manifest-bound inode/hash. Interrupted/fault tests reproduce documented durable phases with real public artifact files/hardlinks, not hidden runtime fault flags. Reject incomplete/malformed artifacts and unrelated identical outputs. Source changes after a completed publication do not invalidate historical snapshots or justify a second write; idempotent repeat only confirms the already owned output. Out-of-band same-user writes may occur after any observation; snapshots remain the staged revision, and original paths never get overwritten. Host root/same-user malicious tampering and lying storage hardware are outside the integrity boundary.
TX-7 Existing validate/compare/baseline/plan/dry-run and Action outputs unchanged. Source version0.3.0 CLI addition; no new package-root persistence API. Real CLI E2E and installed consumer remain mandatory. Help/README, reviewed migration format/recovery/permissions, full pre-commit, Node22/24 CI, independent security/spec verification and actual tracker closure required. Human acceptance separate. No live user migration is run by the agent.

## Risks / mitigations (initially open until proof)

R1 data loss HIGH: no-replace outputs and no original writes; immutable raw snapshots; exact restore proof.
R2 races/interruption HIGH: same-FS atomic links, immutable intent/markers, stable inode+hash and replay recovery; no advisory stale-lock takeover.
R3 path traversal/permission leakage HIGH: fixed artifact names, no-follow regular captures, trusted canonical parent ancestry, owner-only artifacts, explicit targets.
R4 false proof/corruption HIGH: strict manifest/marker schema and content digests, bounded worker replay, candidate/source correspondence, output identity checks.
R5 resource abuse MEDIUM: 1MiB snapshots/depth64, existing operation128 limit, worker5s/128MiB, bounded metadata.
R6 durability MEDIUM: fsync files and directory after publication; unsupported OS/filesystem fails closed. No portable power-failure guarantee beyond OS/local-FS sync contract.
Open questions to falsify: directory fsync support on Mac/CI; invariant when outputs edited/deleted; incomplete stage readability; concurrent same vs different transactions; private publication payload aliasing separated from immutable snapshots. No high risk can remain unmitigated at closure.

## Evidence / acceptance

Red-green CLI regressions cover review corrections. npm run check PASS (77/77 macOS, including installed tarball ESM/TypeScript/CLI). Two independent implementation reviews PASS after corrections; docs review and exact-head CI pending. Human acceptance is #18, separate from technical #16. Final AI state READY_FOR_MANUAL_ACCEPTANCE only for this scope after all required proofs. Human recipe: stage disposable example data, inspect, apply to new file, rerun idempotently, restore to new file, compare exact original bytes and confirm no originals were edited.

Primary mechanism refs: Node22 fs.linkSync/fsyncSync/open flags documentation; POSIX link no-replace semantics. These guarantee filesystem name publication, not atomic replacement of arbitrary concurrently modified live files.

Review-discovered required corrections: (C1) recovery must fsync an already linked output and parent before completion markers, not only new links; (C2) reject equal/aliased transaction-output resources and restore destinations inside managed metadata; (C3) validate both retained publication payload hashes on every capsule load; (C4) apply ownership/ancestry/no-other-user-write checks to captured inputs as well as output parents. Each observable failure received a red→green CLI regression; fsync ordering is checked structurally plus interrupted-phase replay tests.

Darwin ACL extension: POSIX mode bits alone cannot establish the chosen private path profile on macOS. A real ACL-grant regression failed under mode0700. The Darwin path/file checker now rejects grant ACEs using bounded shell-free /bin/ls -ldeb with fixed C locale, allowing deny-only OS ACLs; results cache only by inode/ctime/mode/uid within the process. Linux POSIX ACL grants are constrained by the checked permission mask. Data inputs must be caller/root-owned, not group/world writable; root-owned sticky ancestors are permitted, while writable destinations remain caller-owned. ACL replication remains out of scope. Final independent recheck required.

Recovery durability refinement C5: both independently reviewed recovery paths now confirm+fsync the already-owned output inode and its parent before the completion marker. Existing marker fast returns were removed as well: every successful ensureMarker validates content, fsyncs the marker inode, transaction directory and its parent, without rewriting the marker. This covers interruption after either output or marker link publication but before directory flush. Proof combines direct ordering review with real public on-disk pending-phase replay; no claim of hardware power-failure simulation.
